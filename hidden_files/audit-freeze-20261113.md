# フリーズ総点検レポート（2026-11-13、v780時点のコードに対する監査）

本人の指示「原因を推測で決めず、同じようにループしうる observer と他のフリーズ要因を体系的に全部洗う」への実施記録。
結論：**ハードフリーズ級の自己ループは v767 の1件だけ**で、修正済み（v781で出荷）。他はすべて収束形か対象外書き込み。

## 1. MutationObserver（151件を機械抽出、全件分類）

- コールバック内でDOM書き込みをするもの：38件 → 全件を文脈読みで分類。
  - 危険（無条件の自己書き込み×条件持続）：**v767（L23837）のみ**。自分の class を観測し、`on` が無い間ずっと `classList.remove("v767-imm")` を呼ぶ。Chromium では存在しないクラスの remove でも属性が書き換わり mutation が再発火するため無限ループ（最小再現で確定、下記）。→ `contains` ガードで修正。
  - 収束形（安全と判定）：存在チェック付き append（L2860/L4295/L4522/L4974/L5685/L6625/L7717/L9125/L14586/L14678/L14773 等、HPパネル・ノート系の定番形）、dataset フラグ付き（L5832/L22767/L11944）、値比較付き textContent（L17549）、除去後に再検出されない除去系（L9879/L16203/L19827）、別要素への書き込み（L2035/L2796/L3534/L8672/L19938/L23539 等）、style エンフォーサ（L7456/L7478/L7625、再現テストBで収束を確認）、フラグ収束型（L24226=v774、再現テストEで確認）。
  - 書き込みしないもの：113件（呼び先ヘルパー経由の間接書き込みは動的プローブで担保、下記）。
- 動的裏付け：計測ラッパー（observer コールバック総数・mutation records・live interval 数・longtask）を仕込み、ホーム／写真ビューア開閉×3／X／炎上編突入＋12秒 の各ルートで実行。ページ応答喪失なし、pageerror 0、longtask 最大134ms、interval 数は 230〜234 で安定（増殖なし）。アイドル時のコールバック増分はタイマー駆動の定常範囲（シーンにより3〜4秒で約600〜900回）。

## 2. パターン再現テスト（最小ページ、Chromium、2026-11-13実施）

| テスト | 形 | 結果 |
|---|---|---|
| A | class 観測下で不在クラスの `classList.remove` を無条件実行（v767形） | **無限ループ（確定）** |
| B | style 観測下で同値 `style.display` セット（エンフォーサ形） | 収束（安全） |
| C | subtree 観測下で `textContent` 無条件セット（v773で実際に死んだ形） | **無限ループ（確定）** |
| D | `!==` 比較ガード付き textContent（L17549形） | 収束（安全） |
| E | フラグで1回だけ remove（v774形） | 収束（安全） |
| F | class 観測下で存在するクラスの `classList.add` を無条件実行 | **無限ループ（確定）**＝add 側も同罪 |

法則：**「観測中の属性/ツリーへの無条件書き込み」だけが死ぬ**。classList は add/remove ともノーオプでも属性を書き換える（Chromium）。textContent は同値でもノード差し替えになる。style プロパティの同値セットは mutation を生まない。

## 3. その他のフリーズ要因クラス

- **while（31件）**：全件 bounded。配列走査・兄弟/祖先ウォーク・子数トリム（毎回1つ減る）・TreeWalker・上限ガード付きフィットループ。`while(n===cur)` のシャッフル（L15443）は TRACKS=4件のため終了する（1件なら無限ループ化するので、将来トラックを減らす時は要注意）。
- **for(;;)／while(true)**：0件。
- **requestAnimationFrame（11件）**：時間上限付きカウントアニメーションとスクロール駆動の描画のみ。自己継続ループなし。
- **dispatchEvent（7件）**：input/resize/clock転送/wheel転送。循環なし（clock のハンドラは転送元を叩かない）。
- **プログラム的 .click()（107件）**：大半は「代理ボタン→正規ボタン」の一方向。双方向ペアは bypass フラグ（L13611）／dataset.on ガードで保護済み。計測ルートで stack overflow 系 pageerror 0。
- **setInterval 287件／setTimeout 353件**：静的には自己再帰型の無限予約なし。動的には live 数がルート横断で安定（開閉を繰り返しても増えない）＝積み増しリークなし。
- **scrollIntoView（21件）**：scroll ハンドラ内からの呼び出しなし（フィードバックループなし）。

## 4. 残留観察（フリーズではない、今回は直さない）

- observer が約160個あり、document.body subtree 観測が複数（L6625/L7717/L9125 等）。通常の書き込みでも多数のコールバックが起きる構造で、アイドル時も定常的にコールバックが走る（CPU税）。恒常的な重さの一因ではあるが、ループではない。全面改修は回 regression リスクが高く、フリーズ監査の範囲外として記録のみ。
- 起動時の mutation records は約10万件規模（painter 群の初期 bake）。longtask 最大110ms程度で実害は未確認。本人の実機では起動は重くないという確定事項があるため不介入。

## 5. 今後の実装ルール（この監査から）

1. observer のコールバックで、観測中の要素・属性・ツリーに書く時は「現在値と違う時だけ書く」か「フラグで1回だけ」にする。classList の add/remove は特に無条件で呼ばない。
2. textContent/innerHTML を自分の観測範囲に書く場合は必ず値比較ガード。
3. 新規 observer を足したら、対象画面の開閉を probe で繰り返し、応答喪失がないか見る。
